# Backend

## db
The team shares one Tiger Cloud database (managed Postgres with TimescaleDB). It stores derived channel numbers, cues, calibration metrics, simulator metrics and per-user profiles.

Stored: derived numeric values only.
Never stored: raw video, images, face templates.

You do not need a Tiger Cloud account or any database setup. One person created the database. You only need the connection URL and about five minutes.

### Quick start

All commands run from this folder (backend/db).

1. Get the connection URL from Bailey, privately. This URL has full admin access to the database, so treat it like a password. Use a direct message or a password manager. Never paste it in a shared channel, an issue, a PR, or a commit.

2. Create your own .env file.

`cp .env.example .env`

Open .env and replace the placeholder line with the URL you were given. The file is ignored by git, so it stays on your machine. The file name must stay .env (or another name covered by .gitignore).

3. Install the Python dependency.

`python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt`

4. Load your URL into the terminal. Do this in every new terminal window:

`set -a; source .env; set +a`

5. Check it works.

`python tiger_store.py report`

If you see two tables headed "Latest 2 sessions" and "Per-channel summary", you're connected. Empty tables are fine; they just mean there is no data yet. An error means something is wrong, so see Troubleshooting below.

Windows (PowerShell): instead of steps 3 and 4, run py -m venv .venv, .venv\Scripts\Activate.ps1, pip install -r requirements.txt, then $env:TIMESCALE_SERVICE_URL="<the URL>" in each new window.

New laptop? Repeat the steps, or copy your .env file across.

What you can do
Command	What it does
python tiger_store.py report	Show the latest sessions and per-channel summaries
python tiger_store.py make-fixture	Generate two synthetic test sessions in fixtures/
python tiger_store.py load-session ...	Write one session (frames file + events file) to the database
python tiger_store.py refresh	Materialise the summaries now (optional, they also refresh themselves every minute)
python tiger_store.py delete-profile --profile-id <uuid>	Delete a profile and everything about it

Everyone has admin access, so you can also run psql "$TIMESCALE_SERVICE_URL" -f queries.sql to explore the data. It needs psql installed (on a Mac: brew install libpq, then add it to your PATH).

Rules for the shared database
- You have full admin access, so be careful. Never run DROP, TRUNCATE or a DELETE without a WHERE on the shared database. If you aren't sure, ask first.
- Change the schema through schema.sql, in a PR. Don't make one-off edits in a console, or the repo and the real database drift apart.
- Label your data honestly. Load real recordings with --origin measured. Anything generated by make-fixture or made up for testing must use --origin synthetic_seed. Never present synthetic data as a measured result.
- Clean up after testing. Use a profile name that says it's a test, such as --new-profile "TEST davina", and delete it when you're done with delete-profile.
- Never commit credentials. No URLs, passwords or .env files in git. If you accidentally push one, tell Bailey straight away so the password can be reset.
- No raw video or images, ever. Only derived numbers go in.
- The control loop never waits on the database. Motor control and the stop logic must not depend on a network call. Write to the database after a session or in the background.
  
### Loading a session

A session is two files in JSONL format (one JSON object per line). One is the camera frames and the other is the cue decisions. The exact fields are described at the top of tiger_store.py.

#### Frames (about 30 per second):

json
{"t": 1763700000.033, "channels": {"brow_raise_left": 0.41}, "head": {"yaw": 2.1, "pitch": -0.4, "roll": 0.0}, "confidence": 0.93}

#### Events (one per decision):

json
{"t": 1763700004.5, "cue": "go", "confidence": 0.88, "stop_reason": null}

Load them:

`python tiger_store.py load-session --new-profile "TEST yourname" --tier 1 --origin synthetic_seed \
    --frames fixtures/session_a_frames.jsonl --events fixtures/session_a_events.jsonl`

It prints the profile id and session id. To add a second session to the same profile, use `--profile-id <that id> instead of --new-profile`.

Optional flags: `--calibration cal.json, --sim-metrics '{"cues_per_metre": 3.1}', --demo-visible` (allow aggregated data from this profile in the public demo views).

### Setting up the service from scratch

_Only needed if someone creates a new Tiger Cloud service._

1. Create a Tiger Cloud service (the free tier is enough) and keep the connection string in an ignored credentials file.
2. Apply the schema: `psql "$TIMESCALE_SERVICE_URL" -f schema.sql` (needs psql; do not run it as one transaction, because continuous aggregates can't be created in one). It's safe to re-run, and re-running restores the structure but never restores deleted data.
3. Share the connection URL with the team privately.
4. Reset the password in the Tiger Cloud console after the hackathon, or immediately if the URL ever leaks.

Public demo: point any public dashboard at a login role under demo_reader, never at the admin URL. demo_reader can only read demo_session_summary and demo_channel_trend, which show hashed aliases and aggregates for profiles with consent granted and demo_visible set.

#### Design notes
- signal_samples and control_events are hypertables on ts. profile_id is denormalised into both so per-profile queries, indexes and deletion don't need a join.
- control_events is keyed (session_id, sequence, ts), because a hypertable key must include the time column.
- signal_summary_1min only uses tracking_ok samples, so lost tracking can't inflate a channel's range. session_channel_stats rolls it up per session and channel for the drift trend.
- Compression and retention policies are in schema.sql, commented out.
- Keep a local copy of the demo profiles, and sync here when connected, since the control loop must never wait on the network.
